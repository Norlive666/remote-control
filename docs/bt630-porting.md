# BT630 移植与排障指南

更新日期：2026-10-31。以本仓库 STM32 驱动 `stm32-v3.0.0` 和 Android App `v1.7.0` 为基准；下文函数名、默认参数和行为均对应这两个版本。第 7 节另行解释旧版 `-5` 错误。

本文说明怎样把 BT630 接到新的 STM32 HAL 工程，以及怎样区分手机连接、UART 接收、协议解析和业务控制问题。芯片通用说明见 [STM32 接入文档](stm32.md)，完整帧格式见 [协议文档](../protocol/README.md)。

## 1. 下载与通信链路

- [Android APK v1.7.0](https://github.com/Norlive666/remote-control/releases/download/v1.7.0/remote-control-v1.7.0.apk)：Android 8.0 及以上。
- [STM32 驱动包 v3.0.0](https://github.com/Norlive666/remote-control/releases/download/stm32-v3.0.0/remote-control-stm32-v3.0.0.zip)：H723、F103 两套独立的 `.c/.h`。
- 仓库源码：[H723](../stm32/h723/)、[F103](../stm32/f103/)。一次只加入与芯片匹配的一套。

```text
手机 App → BLE GATT 写入 FFF2 → BT630 → UART TXD → STM32 RX
                                             ↓
                                  字节解析 → CRC/序号检查 → g_rc
```

App 的“已连接”和写入成功，只说明手机侧 BLE 流程完成，不能证明 STM32 已收到或正确解析。当前协议没有 STM32 收包 ACK，必须观察接收端的 `valid_frames` 等状态。

## 2. BT630 与手机端配置

### 模块配置

本接收驱动要求模块把 BLE 收到的控制帧作为原始二进制字节输出到 UART。飞易通列出的默认参数如下：[BT630 官方手册](https://document.feasycom.com/docs/ble/BT630_Multi_EN/latest/MultiRole_Guide.html)。

| 项目 | 本项目使用值 |
| --- | --- |
| BLE 服务 UUID | `0000FFF0-0000-1000-8000-00805F9B34FB` |
| 手机向模块写入 | `0000FFF2-0000-1000-8000-00805F9B34FB` |
| 模块向手机通知 | `0000FFF1-0000-1000-8000-00805F9B34FB` |
| 默认模块 UART | `115200 bit/s`、8 数据位、无校验、1 停止位（8N1） |

同为 BT630，固件功能也可能不同。飞易通 FAQ 区分了透传固件与通过 AT 命令/数据指示收发的多连接固件；不能仅凭型号认定 UART 输出一定是原始 20 字节帧。如果 UART 出现命令头、长度、通道信息等额外封装，需要按对应固件解封装，或选择适用的透传固件。本驱动不解析这些 AT 封装。[官方固件差异说明](https://document.feasycom.com/docs/fsc-faq/EN/latest/faqs.html#bt630-does-this-module-support-transparent-transmission-mode)

需要确认参数时，先断开手机，用适配电平的 USB-UART 连接模块，按当前固件手册查询。例如所引手册提供 `AT+VER`、`AT+BAUD`；命令以 `\r\n` 结束。查询前串口工具本身也必须使用模块当前的波特率。记录返回值后再判断是否修改；不同固件的指令和透传设置应以对应版本手册为准。[官方 AT 命令说明](https://document.feasycom.com/docs/ble/BT630_Multi_EN/latest/MultiRole_Guide.html#at-command-description)

### App 配置

1. 打开手机蓝牙；按 App 要求允许精确位置、开启定位，Android 12 及以上还需允许“附近设备”。这是当前 App 的扫描条件。
2. 点击主面板的 **“FSC-BT630”** 打开连接窗口。v1.6.0 仅保留 BT630，不再需要切换连接模式，旧版模式设置会被忽略。
3. 在 App 内扫描并连接模块；默认配置下无需先到系统蓝牙中配对。系统页面拒绝配对，不能单独证明 BLE GATT 不可连接。
4. 诊断期间先断开其他手机、蓝牙调试器与模块的连接，排除其他客户端影响。
5. 连接后先保持“使能”关闭，确认 STM32 接收正常，再手动开启。

当前 App 仅使用上述 BT630 UUID 组，未提供自定义 UUID。模块名称可以改变；扫描不按名称过滤。手机 App 的发送频率不会自动改变模块 UART 波特率。连接窗口将详细权限说明、UUID、扫描数量及错误诊断放在帮助中，不占用默认设备列表空间。

连接失败或意外断线时，一轮最多尝试 5 次（含首次），间隔 1、2、4、4 秒；稳定就绪满 10 秒后，下一次断线可启动新一轮。主动断开、取消、进入后台会停止重试。每次连接或失联均关闭使能并清零控制量，重连后先发送禁用帧，需用户重新手动使能。服务/特征不匹配、蓝牙关闭或权限不足直接停止，不靠反复重试掩盖配置错误。扫描不能同时干扰已经建立或正在重试的控制链路。

## 3. 接线、反相与固定外设

| 驱动目录 / 芯片 | MCU 接收：模块 TXD → | MCU 发送：→ 模块 RXD | 占用定时器 | 发布包接收极性 |
| --- | --- | --- | --- | --- |
| `stm32/h723/`，STM32H723VGT6 | PD9，USART3 RX，AF7 | PD8，USART3 TX，AF7 | TIM5 | `RC_RX_INVERT=1` |
| `stm32/f103/`，STM32F103C8T6 | PA10，USART1 RX | PA9，USART1 TX | TIM4 | `RC_RX_INVERT=0` |

两端必须共地。UART 使用兼容的 3.3V 逻辑，供电按裸模块或转接板的实际规格。仅接收手机控制数据时，模块 TXD → MCU RX 和共地是必要信号连接；本驱动不主动通过 MCU TX 回传确认。要从 MCU 向模块发 AT 命令，则还需发送通路和相应程序。

**H723 默认反相是为本项目实测板的接口电路设置的，不是 BT630 自身要求。**

| H723 的实际信号路径 | `remote_control.h` 设置 |
| --- | --- |
| BT630 TXD 直接接芯片 PD9，无反相器件 | `#define RC_RX_INVERT 0` |
| 本项目实测板：TXD → CN14 第 3 脚 → R28/Q5 → PD9，信号被反相一次 | `#define RC_RX_INVERT 1`，发布包默认 |

该实测板 CN14 第 1 脚为 GND；其他板卡必须对照自己的原理图。普通 UART 在模块 TXD 处空闲为高，经本板 Q5 后 PD9 空闲为低。万用表只能辅助看静态电平，不能判断字节、波特率和帧格式；这些需要示波器或逻辑分析仪。

F103 这套驱动不支持硬件接收反相，非零 `RC_RX_INVERT` 会编译报错；应使用普通 UART 信号路径，或在硬件上恢复正确极性。

## 4. 在新 HAL 工程中接入

### 加入文件和配置

1. 将对应芯片目录的 `remote_control.c`、`remote_control.h` 复制到工程；把 `.c` 加入构建、头文件目录加入搜索路径。
2. 工程提供正确的芯片 HAL、CMSIS、启动文件、链接脚本、`HAL_Init()` 和 `SystemClock_Config()`；H723 需要基础 RCC/RCCEx 支持。
3. 按接线设置头文件。默认波特率为 115200；H723 直连 PD9 时务必将反相设为 0。

```c
/* 对应 remote_control.h 中的配置；不要复制两个芯片包一起编译。 */
#define RC_DEFAULT_BAUD 115200U
/* H723 经本板 Q5 为 1，普通直连为 0；F103 只能为 0。 */
```

也可通过编译器参数全局覆盖配置，但必须对 `remote_control.c` 的编译生效。只在 `main.c` 中定义宏，不能改变另一个编译单元的配置。

### 初始化和读取

在现有 `main.c` 包含头文件并增加状态变量：

```c
#include "remote_control.h"

volatile HAL_StatusTypeDef g_rc_init_status;
RC_State_t rc_state;
```

在 `HAL_Init()`、系统时钟和已有全部 `MX_*_Init()` 完成之后，目标串口的其他业务启动之前，加入一次初始化：

```c
g_rc_init_status = RC_Init();
if (g_rc_init_status != HAL_OK) {
    Error_Handler();
}
```

随后在原主循环或任务中读取一致快照，并把条件判断接入自己的业务；本驱动不会自动控制电机或更新原工程的 `rc_ctrl`：

```c
RC_GetState(&rc_state);
if (rc_state.link_valid && rc_state.enabled && !rc_state.stopped) {
    /* 使用 rc_state.axes[0..3] 和 rc_state.sliders[0..1]。 */
} else {
    /* 在此使业务输出回到自己的停止/中立状态。 */
}
```

`g_rc` 是全局 `volatile RC_State_t`，可在调试器中直接观察；业务同时读取多个字段时使用 `RC_GetState()`，避免读取到更新了一半的数据。

### 三个初始化接口的区别

| 接口 | 含义 |
| --- | --- |
| `RC_Init()` | 使用头文件 `RC_DEFAULT_BAUD`，发布包默认 115200 |
| `RC_InitBT630()` | 固定 115200，不接受参数 |
| `RC_InitBaud(baud)` | 使用指定 UART 波特率，例如实际模块为 9600 时传 `9600` |

三者使用同一个初始化实现，并遵循同一反相配置。`RC_InitBaud()` 的单位是 bit/s，不是定时器分频、发送周期或连接超时。成功后重复同波特率初始化不重置状态，换波特率则返回 `HAL_BUSY`；`RC_Reset()` 也不会解除硬件占用或修改波特率。需要更换初始化参数时，修改配置后复位 MCU，检查本次返回值。

### `.ioc` 和原有文件怎样处理

| 工程现状 | 处理方法 |
| --- | --- |
| `.ioc` 没配置目标 UART/GPIO/定时器 | 无需增加配置；本驱动直接配置固定外设寄存器 |
| 目标 UART 已经 `MX_USARTx_UART_Init()`，但尚未启用收发业务 | 保留文件和初始化；随后调用 `RC_Init()`，驱动重新设置 UART 参数 |
| 目标 UART 正在供 D-Bus、日志、DMA、中断等业务使用 | 不能并用；先决定串口归属，再停止/移除对这一外设的原业务，或另行移植到空闲外设 |
| TIM5（H723）或 TIM4（F103）已配置或使用 | 即使尚未启动，驱动也可能返回 `HAL_BUSY`；当前实现不接管已启用时钟/中断的目标定时器 |

不需要删除 `usart.c`、`tim.c` 或修改生成的 IRQ 函数。本驱动在对齐 RAM 中复制当前向量表，只替换目标 UART 和定时器入口；成功后独占这些外设，不能继续用原 HAL 句柄操作它们，也不能稍后再次初始化或改写这些时钟、引脚和向量表。

可以保留 CubeMX 串口初始化，不代表可以同时保留原 D-Bus 接收业务。驱动不会自动检测所有轮询访问和未来业务启动，因此软件层面的独占仍需调用方保证。带引导程序或 RTOS 的工程，还应确认后续不会再次覆盖 `SCB->VTOR`。

### 初始化返回值

| 返回值 | 主要检查项 |
| --- | --- |
| `HAL_OK` | 外设初始化成功；仍需验证 UART 信号与有效帧 |
| `HAL_BUSY` | UART DMA/中断/未完成发送、目标定时器占用、F103 USART1 重映射，或已初始化后尝试换波特率 |
| `HAL_ERROR` | 波特率为零，或实际时钟不能得到本驱动支持的 UART/定时器分频 |

忙和参数错误路径保留原状态；详见 [完整占用规则](stm32.md#占用与返回状态)。

## 5. 协议、状态与首次验证

每帧 20 字节，以 `A5 5A` 开始，包含版本、序号、四个有符号轴值、四路滑块值、标志和 CRC。App v1.7.0发送v2帧，驱动v3.0.0也兼容旧v1两路帧，旧帧缺少的两路会清零；旧驱动无法解析新App帧。多字节字段小端；不能把原始字节直接强转为 `RC_State_t`。帧可被拆开或连续到达，接收端逐字节处理，不以一次中断或一次 BLE 写入作为 UART 帧边界。

| 观察项 | 含义 / 正常表现 |
| --- | --- |
| `axes[0..3]` | 左 X、左 Y、右 X、右 Y，范围 -1000～1000；正方向为右、上 |
| `sliders[0..3]` | 四通道的实际整数，0～1000；App 默认三档 0/1/2 |
| `enabled` / `stopped` | 使能 / 停止状态；输出有效需同时满足使能且未停止 |
| `link_valid` | 接受有效新帧后为 1，初始化及超时后为 0 |
| `valid_frames` | 累计接受的有效新帧，包含禁用帧；连续通信时应持续增加 |
| `crc_errors` | 已收集完整候选帧、但 CRC 不匹配的次数；不是所有 UART 或协议错误的总数 |

建议按顺序测试：

1. 观察 `g_rc_init_status == HAL_OK`。
2. 手机选择 BT630 BLE 并连接，保持使能关闭；确认 `valid_frames` 持续增长、`link_valid=1`。此时控制量为零是预期行为。
3. 打开使能，分别移动左右摇杆和默认两个滑块，再添加目标通道3/4的组件，检查字段映射、备注、点按/长按/切换及范围。
4. 松开摇杆应归零；断开蓝牙后，在正确的 1 ms 定时基准下约 300 ms 内应禁用、归零、`stopped=1`、`link_valid=0`。
5. App 重新连接后仍需手动开启使能。STM32 驱动 v2.3.0 起，初始化、重置或接收超时后的首个合法使能帧可以直接恢复输出；手机使能保持开启时，不再要求关闭再开启。旧驱动 v2.2.1 及更早版本仍要求先收到禁用帧。

禁用状态且序号为 0 的合法测试帧如下，CRC 已独立计算：

```text
A5 5A 01 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 2E C2
```

蓝牙调试器须按 HEX 发送这 20 个二进制字节，不能发送字符串 `"A5 5A ..."`。同一序号反复发送只有首次可能计入有效帧；持续验证需要递增序号并重新计算 CRC。完整 CRC 参数、序号规则、保留位和范围限制见 [协议文档](../protocol/README.md)。

调试时可以在私有 `uart_irq()` / `RC_ProcessByte()` 中观察局部字节或内存；`rx` 是静态内部缓冲，不是公开 API。频繁停断点会引发 UART 溢出并干扰超时。不要在循环刷新的监视窗口读取 `RDR`（H723）或 `DR`（F103），读取数据寄存器会消耗待接收字节。

## 6. 按故障层次排查

| 现象 | 优先排查 |
| --- | --- |
| App 搜不到设备 | 蓝牙/定位开关、权限、模块供电和广播、其他连接占用；记录扫描窗口两路计数及错误 |
| 能搜索但连接失败 | App 是否选 BT630 BLE，服务/写入特征是否为 FFF0/FFF2，模块固件和当时连接状态 |
| App 已连接，STM32 接收中断不进 | Init 返回值、实际物理引脚、共地、模块是否输出 UART、NVIC/VTOR 是否被后续代码修改 |
| 能进 UART 中断，数据却异常 | 波特率/8N1、接收反相、错误标志 FE/NE/ORE/PE、实际 UART 时钟、信号质量 |
| `crc_errors` 增加 | 字节丢失/改变、波特率或极性错误、HEX 与文本混淆、固件额外封装、CRC 覆盖范围或字节序错误 |
| 两个计数器都是 0 | 可能没收到帧头或没凑齐帧，也可能版本/范围/序号/恢复条件不符；不能仅凭此认定接线正确或错误 |
| `valid_frames` 增长而控制量为 0 | 手机使能未开、处于停止/禁用，或实际发送值为 0 |
| 数据短暂变化后又归零 | 检查是否超时、有效帧是否持续、序号是否递增，以及定时器是否确实 1 ms 一次 |

不要将“能够进入接收中断”当成接收成功证据。错误或噪声同样可能伴随中断；最终应验证原始字节、CRC、有效帧和状态。

## 7. `BLE 写入失败 -5` 与运行中断连

App v1.5.1 及此前相关版本使用 Nordic Android BLE Library 2.11.0。其 `FailCallback.REASON_TIMEOUT = -5`，含义是请求超时；它不是 STM32 的 CRC 错误，也不是 Android 配对 PIN 错误。[该版本错误码定义](https://github.com/NordicSemiconductor/Android-BLE-Library/blob/2.11.0/ble/src/main/java/no/nordicsemi/android/ble/callback/FailCallback.java)

v1.6.0 改为原生 GATT 连接，参考用户提供的 [bt_mcu](https://gitee.com/xie-rongji/bt_mcu)，保留其扫描、连接、服务发现与特征读写流程，并增加状态检查及可取消重试。源码：

- [`Bt630GattClient.kt`](../android/app/src/main/java/io/github/norlive/remotecontrol/Bt630GattClient.kt)：检查 FFF0/FFF2，等待 FFF1 通知订阅完成后才就绪；优先使用带响应写入，不支持时回落无响应写入。每次写入检查系统返回值和回调状态，超时后关闭失效 GATT。
- [`Bt630Session.kt`](../android/app/src/main/java/io/github/norlive/remotecontrol/Bt630Session.kt)：串行发送最新的 20 字节帧，完成后延迟 20 ms；执行五次上限、间隔、取消及失联禁用。
- [`RemoteViewModel.kt`](../android/app/src/main/java/io/github/norlive/remotecontrol/RemoteViewModel.kt)：连接面板输入与会话状态，收到 FFF1 原始通知可在设置中查看。蓝牙写入成功仍不表示 MCU 已收包。

旧版 `-5` 对应写请求在 1 秒内未完成，旧库超时路径及 App 会结束连接。[旧库超时实现](https://github.com/NordicSemiconductor/Android-BLE-Library/blob/2.11.0/ble/src/main/java/no/nordicsemi/android/ble/TimeoutableRequest.java) 新版仍保留连接 10 秒、写入 1 秒的期限，但将失败阶段和完整诊断放在帮助中，并按上述规则重新建立链路，不把过期控制帧放回发送队列。更换连接实现不等于已经证明所有手机或模块的偶发超时根因都已解决。

如果已经正常控制一段时间后才报错，至少说明此前连接、服务检查和多次写入已完成。应优先调查运行中的无线链路、供电、模块固件/缓冲行为以及手机蓝牙栈/回调；尚无日志时，这些只是待验证方向，不能直接归因于模块设置或 1 秒超时过短。

### 对比测试

1. 手机靠近模块，保持 App 前台，断开其他客户端，在同一位置重复测试，记录多久出现错误。检查模块是否同时发生重启/连接指示变化。
2. 同一手机、同一模块，用蓝牙调试器写入 **同一个 FFF2 特征**，发送 20 字节二进制数据。先每 100 ms 一次，再与每 20 ms 一次对比；记录写入类型、是否启用 FFF1 通知及持续时间。调试器单次连接成功不足以证明持续发送正常。
3. 换手机或换同型号模块，保持其他条件相同，判断故障是否跟随手机、模块或环境。
4. 若仍复现，保留 App 完整错误和 Android 日志；需要时在手机开发者选项开启蓝牙 HCI 日志，按该手机系统的方式导出。目标是区分系统没有交付写请求、链路断开、模块无响应，还是回调没有及时处理。

BT630 模式按名义 50 Hz 计算约 1000 字节/秒；115200、8N1 的 UART 理论上约可发送 11520 字节/秒，所以不能仅凭这个发送量认定 UART 带宽耗尽。实际发送还包含等待写入完成的时间。若模块 UART 降到 9600，则理论 960 字节/秒已低于上述名义负载，需重新评估发送频率和模块缓冲。

不应通过无限重试、堆积旧控制帧或只延长超时来掩盖问题。STM32 仍保留 300 ms 失联归零，但 v2.3.0 驱动允许随后收到的合法使能帧直接恢复。App 自身断开/重连仍要求手动使能；发送频率、写入类型及超时不提供界面配置，本节对比频率是蓝牙调试器中的定位方法。

## 8. 时钟、波特率与“分频改为 2000”的区别

这次其他设备移植的反馈先提到 `rc_initbt630(12000)`，随后更正为“似乎把分频之类的值改为 2000，具体代码已没有”。未拿到当时的函数、寄存器、时钟树或波形，因此本记录仅保留现象，**不将 12000 或 2000 作为移植配置建议，也不认定已找到原因**。

本仓库接口是 `RC_InitBT630(void)`，不接受参数；自定义波特率应调用 `RC_InitBaud(baud)`。如果其他工程出现不同签名，需先核对其文件版本或封装。H723 下载包继续保留 115200 和本板接收反相配置。

### UART 分频影响采样

本驱动采用 16 倍过采样，H723 的 `PRESC=0`（不预分频）。两套实现写入的 BRR 数值可近似理解为：

```text
BRR = round(软件计算的 UART 时钟 / 指定波特率)
实际波特率 ≈ 硬件实际 UART 时钟 / BRR
```

H723 USART3 的时钟由自己的内核时钟选择决定，不能直接拿 CPU 主频代替；F103 本驱动 USART1 使用 PCLK2。若实际振荡源、`HSE_VALUE`、PLL/分频或所取的 USART 时钟与软件计算不一致，修改波特率参数有可能偶然补偿错误比例。应修正时钟认知，再恢复与模块一致的目标波特率。[ST H723 参考手册 RM0468，USART 与 RCC 章节](https://www.st.com/resource/en/reference_manual/dm00603761.pdf)

例如仅在 UART 内核实际为 120 MHz 且配置如上时，115200 对应 BRR 约 1042；相同条件下 BRR=2000 则约为 60000 bit/s。这个示例不是所有开发板的应填数值。`BRR` 是分频编码，不能套用定时器的 `PSC+1` 规则。

要确认 UART，建议在模块 TXD 处用逻辑分析仪测位宽：115200 约 8.68 μs/bit，12000 约 83.33 μs/bit。再核对 MCU 的时钟来源、BRR、过采样、预分频、8N1 和接收极性。不要将手机 BLE 连接间隔或发送周期当作 UART 波特率。

### 定时器分频影响超时基准

本驱动定时器按向上计数、内部时钟运行时，更新周期为：

```text
T_update = (PSC + 1) × (ARR + 1) / f_TIM
```

目标是约 1 ms 更新一次，由中断调用 `RC_Tick1ms()`；连续 300 个计时周期没有有效新帧就归零。`f_TIM` 要按实际 APB 分频和 H723 的 TIMPRE 规则确定，不能一概等同 PCLK 或 CPU 主频。

改定时器 PSC/ARR，通常不会直接修正 UART 的位采样，但会改变“300 次”实际持续多久。例如实际周期只有 0.1 ms，名义 300 ms 的超时会变成约 30 ms，可能出现已经接收但控制量很快又清零的现象。若改的是上游共享时钟，也可能同时影响 UART 和定时器，必须结合改动位置判断。

因此，类似“改成 2000 后正常”至少应补充：改动符号/寄存器、改前改后数值、实际时钟、UART 位宽，以及 `valid_frames`、`crc_errors`、超时归零的变化，才能区分采样错误与超时问题。

## 9. 移植到其他芯片或外设的边界

当前两文件驱动只针对表中两款芯片和固定 UART/定时器/引脚，没有运行时选择外设的 API。更换芯片、USART 或引脚不能仅修改一个名称；需要逐项核对时钟源及门控、GPIO 复用、寄存器布局、错误清除方式、IRQ 编号、向量表尺寸/对齐、缓存处理和定时器频率，再编译及实测。

不能直接把普通 USART 的 BRR 公式用于 LPUART，或把 H723 的反相设置用于 F103。库版本、编译器中的芯片宏与实际芯片也要一致。自定义时钟后应验证 UART 位宽和定时周期，而不只检查 `HAL_OK`。
